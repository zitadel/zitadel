# Follow-up: the 503 bursts of 2026-08-27

Two bursts, six hours apart, on different targets. Burst 1 was found first and most of
this note was written about it; burst 2 is seven times larger and is what makes the pair
worth a post-mortem rather than a shrug.

## Status as of 2026-08-28

The metric half of the investigation is done. The log half was run with broken filters and must
be repeated. Nothing here is concluded yet; the sections below are the chronological record and
this block is the summary.

### Established

- Two bursts on 2026-08-27, both HTTP 503 `Service error -27` -- an HTML page from the Google
  frontend, not a Zitadel JSON error. Burst 1: `manipulate_user`, 13:43:19-13:44:13, 150 requests.
  Burst 2: `human_password_login`, 19:37-19:44, 1,044 requests. Both bounded, then silence.
- **No container startups in any of the eleven test windows.** `container/startup_latencies`
  returned empty distributions throughout and instance count was constant at 7.
- **The two bursts have different server-side signatures.** In burst 1's window there were
  **zero** log entries at `severity>=WARNING`. In burst 2's there were **at least 200**, and that
  200 was the query limit, reached within the first ~2 seconds of a 20-minute window.
- **The 2026-08-26 sweep produced no 503s at all**, on any of its eleven targets. Same instance,
  same deployment, roughly 24 hours earlier.

### Ruled out, provisionally

- **Container restart or replacement.** This was the original working hypothesis, on the grounds
  that a bounded burst followed by silence looks like something being replaced. The startup metric
  does not support it: a replaced container starts, and a start would appear. Provisional only
  because it rests on one metric being both correct and complete.

### Open questions, in the order worth answering

1. **What do burst 2's errors actually say?** At least 200 ERROR entries and we have not read one
   of them. The filters used `textPayload:` terms against a service that logs structured JSON, so
   they matched nothing, and the output format rendered the payload column blank. This is the
   single highest-value unknown and it is entirely self-inflicted.
2. **How many errors are there really?** 200 in two seconds, truncated. Over twenty minutes the
   true figure could be in the thousands, and 1,044 client-observed 503s may be a small fraction
   of what the server logged -- or unrelated to it.
3. **Did the 503s reach Cloud Run at all?** The `httpRequest.status=503` queries came back empty,
   which the section below reads as "the frontend rejected them before they arrived". **Do not
   accept that yet.** If request logging is not enabled on this service the query returns nothing
   regardless. Establish the control first: confirm the service emits *any* `httpRequest` entry,
   in any window. Only then is an empty result evidence.
4. **Why is burst 1 silent and burst 2 noisy?** Same HTTP symptom, opposite server-side signature.
   Two causes wearing the same error page is at least as likely as one, and the note's earlier
   framing -- that the pair is the finding -- assumed a single mechanism it had not established.
5. **Which container instances were involved?** The `instance_id` label rendered empty for every
   entry. Unknown whether `labels."run.googleapis.com/instance_id"` is the wrong path for this
   service or genuinely unset. Check one known-good entry's full JSON before trusting any
   instance-level conclusion.
6. **What is `Service error -27`?** Used throughout this note as an identifier and nowhere
   explained. It is a Google frontend string; if it names the layer that rejected the request, it
   answers question 3 without any log query at all.
7. **Why only the 27th?** The 26 August sweep was clean. The instance's feature flags were changed
   at **13:35:31Z on the 27th, eight minutes before burst 1**. That is close enough to be worth
   checking and far too neat to trust: burst 2 came six hours later, so a one-off configuration
   change does not cover both. Treat as a lead, not a cause.
8. **Does it recur?** Two bursts on one day and none the day before. Whether this reproduces is
   unknown, and it determines whether this is worth an issue or a footnote.

Weak signal, recorded so it is not rediscovered as though it were new: both bursts fell on the two
targets that create users in bulk. With n=2 that is barely distinguishable from coincidence.

A bounded burst followed by silence. This is not the shape of a service under sustained

class from everything in the catalogue in `skills/marvin.md`, all of which are application

## What to query, in Cloud Shell

Local `gcloud` on the load generator VM cannot do this: the compute service account was
created without the logging scope and returns
`PERMISSION_DENIED ... ACCESS_TOKEN_SCOPE_INSUFFICIENT`. Cloud Shell is authenticated.

Deployment: project `zitadel-cloud`, Cloud Run service `zitadel-qa-us1-cr-us-central1`
(us-central1), Cloud SQL `zitadel-cloud:us1`.

Window is padded to 13:38-13:50 deliberately: the cause precedes the effect.

    W_START=2026-08-27T13:38:00Z
    W_END=2026-08-27T13:50:00Z
    SVC=zitadel-qa-us1-cr-us-central1

### 1. Panics and fatal errors

    gcloud logging read \
      "resource.type=\"cloud_run_revision\"
       AND resource.labels.service_name=\"$SVC\"
       AND timestamp>=\"$W_START\" AND timestamp<=\"$W_END\"
       AND (textPayload:\"panic\" OR textPayload:\"fatal error\"
            OR textPayload:\"goroutine\" OR jsonPayload.message:\"panic\")" \
      --project=zitadel-cloud --limit=100 --order=asc \
      --format='table(timestamp,severity,textPayload)'

### 2. Container restarts / new instance starts

    gcloud logging read \
      "resource.type=\"cloud_run_revision\"
       AND resource.labels.service_name=\"$SVC\"
       AND timestamp>=\"$W_START\" AND timestamp<=\"$W_END\"
       AND (textPayload:\"STARTUP\" OR textPayload:\"Container called exit\"
            OR textPayload:\"Memory limit\" OR textPayload:\"terminated\"
            OR severity>=WARNING)" \
      --project=zitadel-cloud --limit=200 --order=asc \
      --format='table(timestamp,severity,labels."run.googleapis.com/instance_id",textPayload)'

Group by `instance_id`: an id first appearing at ~13:43 is a new container, which is the
answer. The v4.17.1 sweep recorded instance count flat at 7 throughout, so any change is
directly comparable against that baseline.

### 3. Instance count around the burst

    gcloud monitoring time-series list \
      --project=zitadel-cloud \
      --filter='metric.type="run.googleapis.com/container/instance_count"
                AND resource.labels.service_name="'"$SVC"'"' \
      --interval-start-time=$W_START --interval-end-time=$W_END \
      --format='table(points[].interval.endTime,points[].value.int64Value)'

`tools/fetch-gcp-metrics.sh` already does the metric half for a given window and can be
pointed at 13:38-13:50 instead of a full test window.

### 4. Who emitted the 503 - Cloud Run or the load balancer

    gcloud logging read \
      "resource.type=\"cloud_run_revision\"
       AND resource.labels.service_name=\"$SVC\"
       AND httpRequest.status=503
       AND timestamp>=\"$W_START\" AND timestamp<=\"$W_END\"" \
      --project=zitadel-cloud --limit=100 --order=asc \
      --format='table(timestamp,httpRequest.status,httpRequest.requestUrl)'

If Cloud Run logged 150 matching 503s, the requests reached it. (Not 29 -- that is only
the subset that surfaced as thrown k6 errors; see the addendum.)

**An empty result is not yet evidence of anything** -- see open question 3. It means "the
frontend rejected them before they arrived" only once the service is confirmed to emit
`httpRequest` entries at all. Untested, this query cannot distinguish an infrastructure finding
from a disabled log.

### 5. Revision / deployment activity

    gcloud logging read \
      "protoPayload.serviceName=\"run.googleapis.com\"
       AND resource.labels.service_name=\"$SVC\"
       AND timestamp>=\"2026-08-27T13:00:00Z\" AND timestamp<=\"$W_END\"" \
      --project=zitadel-cloud --limit=50 --order=asc \
      --format='table(timestamp,protoPayload.methodName,protoPayload.authenticationInfo.principalEmail)'

Rules out someone deploying over the top of a running benchmark. It has happened.

## Burst 2 -- human_password_login @ 600 VUs, 19:37-19:44

Found after burst 1 and not covered by the queries above. It is the larger of the two by a
wide margin:

| | burst 1 | burst 2 |
| --- | --- | --- |
| target | `manipulate_user` (200 VUs) | `human_password_login` (600 VUs) |
| window (UTC) | 13:43:19 - 13:44:13 | 19:37 - 19:44 |
| duration | 55 s | ~7 min |
| count | 150 | **1,044** |
| position in run | ~2 min in | ~13 min in |
| recurrence | none in the following 25 min | none after |

Same signature: HTTP 503 `Service error -27`, an HTML page from the Google frontend, bounded,
then silence. Six hours and four intervening targets apart.

**The comparison is the finding, not either burst alone.** Two possibilities, thought at the
time to be distinguishable from the logs:

> Superseded by the 2026-08-28 collection, which found burst 1 silent and burst 2 noisy at
> `severity>=WARNING`. Both branches below assume a single shared mechanism, which is now the
> thing in question rather than the premise. Retained as the reasoning of the time.


- *Same instance id churning twice* -- one unhealthy container being replaced, twice. That is
  an infrastructure fault and belongs to whoever owns the deployment.
- *Different instance ids* -- something in the workload triggers replacement. That is ours,
  and the fact that both bursts occurred during the two targets that create users in bulk
  would then stop being a coincidence.

Note also what burst 2 is **not**: `human_password_login` reported 8,178 request timeouts
spread evenly across the whole run at 125-360/min. Those are ZITADEL under load and are the
number to read. The 1,044 platform 503s are a separate population and the page reports them
separately. Do not let the post-mortem collapse them back together.

## Results of the 2026-08-28 collection -- read the caveat before the findings

The log half of the first collection was **partly invalid** and must be re-run. The filters
matched only `textPayload`, and Zitadel logs structured JSON, so every `textPayload:` term
matched nothing and the display column rendered blank even where entries existed. Fixed in
`tools/fetch-gcp-all.sh` (jsonPayload filters, payload shown, limit raised 200 -> 5000, and a
loud warning when a query hits its cap).

What survives that caveat, because `severity>=WARNING` is payload-agnostic:

| | burst 1 (13:38-13:50) | burst 2 (19:30-19:50) |
| --- | --- | --- |
| entries at severity >= WARNING | **0** | **>= 200, truncated at the limit** |
| span of the 200 sampled | -- | 19:30:00-19:30:0x, i.e. ~2 seconds |

**The two bursts do not have the same signature**, which contradicts the working assumption
above. Burst 1 produced no warnings or errors at all; burst 2 produced at least 200 in the first
two seconds of the window alone, so the true count over 20 minutes is likely in the thousands.
Their content is unknown -- that is exactly what the broken filter cost.

From the metric side, which was not affected:

- **No container startups in any window.** `container/startup_latencies` returned empty
  distributions across all eleven test windows, and instance count was constant at 7.
- Therefore **the container-restart hypothesis is not supported.** Whatever produced these 503s,
  it was not Cloud Run replacing an instance during the run.

Do not conclude "the frontend rejected the requests before Cloud Run saw them" from the empty
`*_503s.txt` files. That query filtered `httpRequest.status=503`, and if request logging is not
enabled on this service it returns nothing regardless of what happened. **Establish that control
first**: confirm the service emits `httpRequest` entries at all, in any window, before reading an
empty result as a negative.

## Why it matters for the page

If this was a container restart, the 29 failures are a deployment event and must be reported
as such rather than as a Zitadel failure rate. If there was a panic, that is a defect and
worth an issue of its own. Either way the page states what happened; an unexplained 503
burst rendered as a plain failure count would be the "true and misleading" category again.
