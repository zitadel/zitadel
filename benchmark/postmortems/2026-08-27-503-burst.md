# Follow-up: the 503 burst during manipulate_user @ 200 VUs

Run: `manipulate_user`, 200 VUs, 1800s, start_utc 2026-08-27 13:41:09 UTC
Log: `summaries/manipulate_user_20260827T134109Z.log`
Org: `load-test-2026-08-27T13:41:18.586Z` (388127602272919105)
Flags: `improvedPerformance` = PROJECT_GRANT, PROJECT, USER_GRANT, ORG_DOMAIN_VERIFIED
       (captured before the run in `..._flags.json`; sequence 7, set 13:35:31Z)

## What was observed

29 errors, all `503 Server Error ... Service error -27`, an HTML page from the Google
frontend rather than a Zitadel JSON error. All of them on user creation.

    first   2026-08-27T13:43:19Z  (CSV; k6 error lines showed 13:43:21)
    last    2026-08-27T13:44:13Z  (CSV; k6 error lines showed 13:43:57)
    count   150 failed requests (29 surfaced as thrown errors on user creation)
    window  55 seconds, ~2 minutes into the run
    other error classes: 75 request timeouts, 14:08:48-14:11:02 - UNRELATED, see below

A bounded burst followed by silence. This is not the shape of a service under sustained
load; it is the shape of something being restarted or replaced. It is a different failure
class from everything in the catalogue in `skills/marvin.md`, all of which are application
or harness level.

## What to query, in Cloud Shell

Local `gcloud` on the load generator VM cannot do this: the compute service account was
created without the logging scope and returns
`PERMISSION_DENIED ... ACCESS_TOKEN_SCOPE_INSUFFICIENT`. Cloud Shell is authenticated.

Deployment: project `zitadel-cloud`, Cloud Run service `zitadel-qa-us1-cr-us-central1`
(us-central1), Cloud SQL `zitadel-cloud:us1`.

Window is padded to 13:38-13:50 deliberately: the cause precedes the effect.

    W_START=2026-08-27T13:38:00Z
    W_END=2026-08-27T13:50:00Z
    SVC=zitadel-qa-us1-cr-us-central1

### 1. Panics and fatal errors

    gcloud logging read \
      "resource.type=\"cloud_run_revision\"
       AND resource.labels.service_name=\"$SVC\"
       AND timestamp>=\"$W_START\" AND timestamp<=\"$W_END\"
       AND (textPayload:\"panic\" OR textPayload:\"fatal error\"
            OR textPayload:\"goroutine\" OR jsonPayload.message:\"panic\")" \
      --project=zitadel-cloud --limit=100 --order=asc \
      --format='table(timestamp,severity,textPayload)'

### 2. Container restarts / new instance starts

    gcloud logging read \
      "resource.type=\"cloud_run_revision\"
       AND resource.labels.service_name=\"$SVC\"
       AND timestamp>=\"$W_START\" AND timestamp<=\"$W_END\"
       AND (textPayload:\"STARTUP\" OR textPayload:\"Container called exit\"
            OR textPayload:\"Memory limit\" OR textPayload:\"terminated\"
            OR severity>=WARNING)" \
      --project=zitadel-cloud --limit=200 --order=asc \
      --format='table(timestamp,severity,labels."run.googleapis.com/instance_id",textPayload)'

Group by `instance_id`: an id first appearing at ~13:43 is a new container, which is the
answer. The v4.17.1 sweep recorded instance count flat at 7 throughout, so any change is
directly comparable against that baseline.

### 3. Instance count around the burst

    gcloud monitoring time-series list \
      --project=zitadel-cloud \
      --filter='metric.type="run.googleapis.com/container/instance_count"
                AND resource.labels.service_name="'"$SVC"'"' \
      --interval-start-time=$W_START --interval-end-time=$W_END \
      --format='table(points[].interval.endTime,points[].value.int64Value)'

`tools/fetch-gcp-metrics.sh` already does the metric half for a given window and can be
pointed at 13:38-13:50 instead of a full test window.

### 4. Who emitted the 503 - Cloud Run or the load balancer

    gcloud logging read \
      "resource.type=\"cloud_run_revision\"
       AND resource.labels.service_name=\"$SVC\"
       AND httpRequest.status=503
       AND timestamp>=\"$W_START\" AND timestamp<=\"$W_END\"" \
      --project=zitadel-cloud --limit=100 --order=asc \
      --format='table(timestamp,httpRequest.status,httpRequest.requestUrl)'

If Cloud Run logged 29 matching 503s, the requests reached it. If it logged none, the
frontend rejected them before they ever arrived, and this is an infrastructure finding with
nothing to do with Zitadel.

### 5. Revision / deployment activity

    gcloud logging read \
      "protoPayload.serviceName=\"run.googleapis.com\"
       AND resource.labels.service_name=\"$SVC\"
       AND timestamp>=\"2026-08-27T13:00:00Z\" AND timestamp<=\"$W_END\"" \
      --project=zitadel-cloud --limit=50 --order=asc \
      --format='table(timestamp,protoPayload.methodName,protoPayload.authenticationInfo.principalEmail)'

Rules out someone deploying over the top of a running benchmark. It has happened.

## Why it matters for the page

If this was a container restart, the 29 failures are a deployment event and must be reported
as such rather than as a Zitadel failure rate. If there was a panic, that is a defect and
worth an issue of its own. Either way the page states what happened; an unexplained 503
burst rendered as a plain failure count would be the "true and misleading" category again.

## Addendum after the run completed

The full status breakdown (`..._status.txt`, taken while the CSV still existed) shows the
run contained **two unrelated failure populations**, separated by 25 minutes of clean traffic:

    error_code  reqs  first_utc             last_utc
    1503         150  2026-08-27 13:43:19   2026-08-27 13:44:13   <- infrastructure
    1050          75  2026-08-27 14:08:48   2026-08-27 14:11:02   <- the known wall

Only the first population is the subject of this note. The second is the documented
degradation-over-churn behaviour and is expected.

The burst was larger than the k6 error lines suggested: 150 failed requests, of which only
29 surfaced as thrown errors (user creation). The other 121 hit update/lock/delete, where a
failed check does not throw. Query window 13:38-13:50 remains correct.

CSV retained at `output/manipulate_user_27-13:41:10.csv` (0.17 GB) pending this post-mortem,
rather than deleted by `postprocess.sh` as usual. Delete it once the GCP side is answered.
