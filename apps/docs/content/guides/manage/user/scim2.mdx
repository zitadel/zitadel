Zitadel’s **[SCIM v2](https://scim.cloud/) service provider interface** enables standardized provisioning and lifecycle management of users and other instance resources.
By implementing the official *System for Cross-domain Identity Management (SCIM) v2.0* specification, Zitadel allows seamless and automated user creation, updates, deactivation, and deprovisioning across systems.

## API

For full reference details of Zitadel’s SCIM API, consult the API documentation [here](/apis/scim2).

## Provisioning domain

A **provisioning domain** represents an external administrative domain—separate from the service provider—typically introduced for legal, organizational, or technical reasons.
Refer to the SCIM specification definitions in **RFC7643**:
https://datatracker.ietf.org/doc/html/rfc7643#section-1.2

Zitadel uses provisioning domains to scope the handling of the SCIM **`externalId`**, ensuring that different customers or systems provisioning users do not conflict with each other.

### Setting a provisioning domain

A provisioning domain can be assigned to a **service account** by adding the following metadata entry:

- **Key:** `urn:zitadel:scim:provisioningDomain`
- **Value:** the name of the provisioning domain

### How Zitadel stores `externalId`

If a service account has a provisioning domain set, any SCIM `externalId` provided during user provisioning or lookup is stored under:
`urn:zitadel:scim:{provisioningDomain}:externalId`

If *no* provisioning domain is configured, Zitadel falls back to a simplified metadata key:
`urn:zitadel:scim:externalId`

This ensures that different provisioning sources remain isolated, and the correct `externalId` is returned when queried through SCIM.

## Settings

This section provides details on the runtime settings of the SCIM interface of Zitadel.

### Defaults

- Emails from SCIM are treated as **verified**
- Phone numbers from SCIM are treated as **verified**
- Bulk SCIM operations can include up to **100 operations**
- Maximum SCIM request body size is **1 MB**

This behavior can be adjusted through the Zitadel runtime settings:

```yaml
SCIM:
  EmailVerified: true
  PhoneVerified: true
  MaxRequestBodySize: 1_000_000
  Bulk:
    MaxOperationsCount: 100
 ```

## Limitations

Zitadel’s SCIM implementation follows the core SCIM specification but includes the following limitations.

### Supported schemas

Zitadel supports the SCIM User schema (`urn:ietf:params:scim:schemas:core:2.0:User`)
and the SCIM Group schema (`urn:ietf:params:scim:schemas:core:2.0:Group`).
Other extended schemas are not supported.

### Groups

The `/Groups` endpoint supports create, get, list, replace (`PUT`), update (`PATCH`), and delete.
Group lookup supports filters on `displayName` (case-insensitive), `id`, and `externalId` (case-exact equality), with `startIndex` and `count` pagination.
GET and list responses include members by default; `excludedAttributes=members` omits them.

#### Okta and Microsoft Entra ID

Use `externalId` for stable group matching; `displayName` remains available for providers that match by name.
The external ID is persisted per organization and provisioning source, using the same
`urn:zitadel:scim:provisioningDomain` service-account metadata as user provisioning.
A rename preserves the binding. Duplicate external IDs within the same organization and source return HTTP 409;
the same ID can be used in a different organization or source. External IDs are case-exact.
GET and list return only the external ID for the calling source.

POST and PUT accept `externalId`; PATCH can add, replace, or remove it. Omitting it from PUT clears
only the calling source's binding. Removing a binding or deleting the group releases the ID for reuse.
Identity changes commit atomically with name and membership changes, and emit `group.external_id.set` events.
The following provisioning payloads are supported:

* Rename using `path: "displayName"`, or a pathless `value: {"displayName": "Engineering"}`.
* Add members using `path: "members"` and an array of user references.
* Okta removal using `path: "members[value eq \"user-id\"]"`.
* Entra removal using `path: "members"` and an array containing only the users to remove. Other memberships are preserved.
* Replace all members using `op: "replace"`, or remove all members using `op: "remove"` without a value.

Operation names are case-insensitive, including Entra's `Add`, `Replace`, and `Remove`.
Successful PATCH requests return HTTP 204. Repeated additions and removals are idempotent.
Members must already exist in the same organization as the group.

Create with members, PUT, and a batch of PATCH operations validate before committing their changes in one transaction.
A failed mutation does not leave a partial rename or membership change. Reads use eventually consistent projections.
Group writes check the group revision at commit and retry conflicting operations from fresh state, with at most three attempts.
Continued contention returns HTTP 409; retry the request. External ID reservations belong to the claiming group,
so stale releases cannot remove another group’s binding. Group changes, group grants, user deletion, and organization
deletion share a database transaction lock per instance. Deletion discovers memberships from authoritative events,
including changes that have not reached the read projections, and commits the cascade in that same transaction.

### Group notifications for headless applications

Native group and membership events are available to Actions v2 event targets for application integration.
Matching webhook jobs commit in the same transaction as the group change. Delivery uses the existing Actions
worker behavior and has no ordering guarantee across events, workers, or replicas.

Receivers should handle duplicate and out-of-order notifications. The combination of `instanceID`,
`aggregateType`, `aggregateID`, and `sequence` identifies an event; `sequence` is specific to that aggregate,
not the organization or target. Subscriptions can omit events, so sequences need not be contiguous.
Discarding older membership deltas can lose independent changes. Reconcile current group state instead,
accounting for eventually consistent reads with retries or periodic reconciliation.

Webhook retry reliability is unchanged by SCIM group support: target errors may cancel a job or be ignored,
and queued jobs can expire. Reliable retry and failed-message recovery require separate Actions changes.

Zitadel groups are **flat**:

* Group members must be users. Members of type `Group` (nested groups, allowed by RFC 7643) are rejected
  with an explicit error instead of being misinterpreted.
* The read-only `groups` attribute on User resources lists the user's group memberships,
  always with `type: "direct"` (RFC 7643 section 4.1.2), since indirect memberships cannot exist.

### Required attributes

In addition to SCIM-standard required fields, Zitadel requires:

* `name.familyName`
* `name.givenName`
* `emails`: at least one email is required

### Duplicated attribute mapping

The SCIM user attributes `name.formatted` and `displayName` are both mapped to the `profile.displayName` attribute in
Zitadel.
If both are provided, `displayName` always takes precedence and is the value that will be stored and returned in future SCIM queries.
