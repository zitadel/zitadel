## 1. Introduction

This guide will walk you through the steps to migrate users from **Firebase Authentication** to **ZITADEL**. Firebase hashes passwords with its own modified scrypt algorithm. ZITADEL can verify these hashes, so you can choose between three migration strategies based on your requirements.

**What you'll learn with this guide**
- How Firebase password hashes work and how ZITADEL verifies them
- Three migration strategies: Bulk Import with Password Hashes, Bulk Import with Password Reset, and Just-In-Time (JIT) Migration
- How to export user data from Firebase
- Performing the user import via ZITADEL's API
- Testing and validating the migration

---

## 2. Understanding Firebase Password Hashes

### 2.1. Firebase Modified Scrypt

Firebase uses a **modified scrypt algorithm**. Some parameters are the same for the whole Firebase project:

- signer key
- salt separator
- rounds
- memory cost

Each user also has their own salt.

ZITADEL can verify these hashes with the `firebasescrypt` verifier. This means you can import Firebase password hashes, and your users can keep their passwords.

The verifier is not enabled by default. The system administrator must enable it in the [runtime configuration](/self-hosting/manage/configure).
If you cannot enable the verifier, use the Bulk Import with Password Reset strategy or the JIT Migration strategy.

---

## 3. Migration Strategy Overview

You have three options for migrating your Firebase users to ZITADEL:

| Strategy | User Experience | Complexity | Best For |
|----------|----------------|------------|----------|
| **Bulk Import with Password Hashes** | Users keep their password | Low | Any user base, when the `firebasescrypt` verifier can be enabled |
| **Bulk Import + Password Reset** | Users must reset password on first login | Low | Smaller user bases, planned maintenance windows |
| **Just-In-Time (JIT) Migration** | Seamless, transparent migration | Medium | Larger user bases, zero-downtime requirements |

## 4. Prerequisites

### 4.1. Create a ZITADEL Instance and Organization

You'll need a target organization in ZITADEL to import your users. You can create a new organization or use an existing one.

If you don't have a ZITADEL instance, you can [sign up for free here](https://zitadel.com) to create a new one for you.
See: [Managing Organizations in ZITADEL](https://zitadel.com/docs/guides/manage/console/organizations-overview).

> **Note:** Copy your Organization ID since you will use the id in the later steps.

### 4.2. Install Firebase CLI (for export)

Install the Firebase CLI to export user data:

```
npm install -g firebase-tools

Authenticate with your Firebase project:

firebase login
```

### 4.3. Obtain Access Token for API Access

To call the ZITADEL Admin API, you need to authenticate using a **Service Account** with the `IAM_OWNER` Administrator role.

There are two recommended authentication methods:

- **Client Credentials Flow**
  [Learn how to authenticate with client credentials.](https://zitadel.com/docs/guides/integrate/service-accounts/client-credentials)

- **Personal Access Token (PAT)**
  [Learn how to create and use a PAT.](https://zitadel.com/docs/guides/integrate/service-accounts/authenticate-service-accounts#personal-access-token)

**Reference:** [Service Accounts & API Authentication](https://zitadel.com/docs/guides/integrate/service-accounts/authenticate-service-accounts#authentication-methods)

## 5. Strategy 1: Bulk Import with Password Hashes (Keep Passwords)

This approach imports all users at once together with their Firebase password hashes. Users log in with their existing password.

### 5.1. Get the Password Hash Parameters

Open the Firebase console and go to **Authentication** and then **Users**.
Open the three dot menu above the user list and select **Password hash parameters**.

Firebase shows the parameters of your project:

```
hash_config {
  algorithm: SCRYPT,
  base64_signer_key: jxspr8Ki0RYycVU8zykbdLGjFQ3McFUH0uiiTvC8pVMXAn210wjLNmdZJzxUECKbm0QsEmYUSDzZvpjeJ9WmXA==,
  base64_salt_separator: Bw==,
  rounds: 8,
  mem_cost: 14,
}
```

Copy `base64_signer_key`, `base64_salt_separator`, `rounds` and `mem_cost`.

> **Note:** The signer key is a secret. Anyone who has it together with the exported hashes can try to guess the passwords of your users. Do not share it or commit it to source control.

### 5.2. Export Users from Firebase

Export your Firebase users to a JSON file:

```
firebase auth:export users.json --format=json --project YOUR_PROJECT_ID
```

This creates a `users.json` file containing all user data. Each user with a password has a `passwordHash` and a `salt` field.

### 5.3. Enable the Firebase Verifier

The system administrator enables the `firebasescrypt` verifier in the [runtime configuration](/self-hosting/manage/configure):

```yaml
SystemDefaults:
  PasswordHasher:
    Verifiers:
      - "firebasescrypt"
```

Or with an environment variable:

```
ZITADEL_SYSTEMDEFAULTS_PASSWORDHASHER_VERIFIERS='firebasescrypt'
```

If you need more than one verifier, separate them with a comma, for example `'md5,firebasescrypt'`.
Restart ZITADEL after you change the configuration.

The default limits accept the Firebase defaults, `mem_cost` 14 and `rounds` 8.
If your project uses other values, adjust `SystemDefaults.PasswordHasher.Limits.FirebaseScrypt` in the runtime configuration.
`MinLN` and `MaxLN` limit `mem_cost`. `MinR` and `MaxR` limit `rounds`.

> **Note:** Keep the verifier enabled until all imported users have logged in once. ZITADEL needs it for the first login of each imported user. If you disable it earlier, those users cannot log in.

### 5.4. Build the Encoded Password Hash

ZITADEL expects one string per user that contains the hash and all parameters:

```
$firebasescrypt$ln=<mem_cost>,r=<rounds>$<salt>$<passwordHash>$<base64_salt_separator>$<base64_signer_key>
```

| Part | Value | Source |
|------|-------|--------|
| `<mem_cost>` | Memory cost, for example `14` | `mem_cost` from the password hash parameters |
| `<rounds>` | Rounds, for example `8` | `rounds` from the password hash parameters |
| `<salt>` | Salt of the user | `salt` of the user in `users.json` |
| `<passwordHash>` | Password hash of the user | `passwordHash` of the user in `users.json` |
| `<base64_salt_separator>` | Salt separator of the project | `base64_salt_separator` from the password hash parameters |
| `<base64_signer_key>` | Signer key of the project | `base64_signer_key` from the password hash parameters |

All values except `mem_cost` and `rounds` are base64. Copy them as they are.
ZITADEL accepts standard and URL-safe base64, with or without `=` padding.

Example (the public sample from [firebase/scrypt](https://github.com/firebase/scrypt), the password is `user1password`):

```
$firebasescrypt$ln=14,r=8$42xEC+ixf3L2lw==$lSrfV15cpx95/sZS2W9c9Kp6i/LVgQNDNC/qzrCnh1SAyZvqmZqAjTdn3aoItz+VHjoZilo78198JAdRuid5lQ==$Bw==$jxspr8Ki0RYycVU8zykbdLGjFQ3McFUH0uiiTvC8pVMXAn210wjLNmdZJzxUECKbm0QsEmYUSDzZvpjeJ9WmXA==
```

### 5.5. Transform Firebase Data to ZITADEL Format

You need to map Firebase fields to ZITADEL's schema. Here's a sample transformation:

**Firebase Export Sample:**
```json
{
  "users": [
    {
      "localId": "firebase-user-123",
      "email": "user@example.com",
      "emailVerified": true,
      "displayName": "John Doe",
      "createdAt": "1609459200000",
      "passwordHash": "...",
      "salt": "..."
    }
  ]
}
```

**ZITADEL Import Format:**
```json
{
  "dataOrgs": {
    "orgs": [
      {
        "orgId": "<your-org-id>",
        "humanUsers": [
          {
            "userId": "firebase-user-123",
            "user": {
              "userName": "user@example.com",
              "profile": {
                "firstName": "John",
                "lastName": "Doe"
              },
              "email": {
                "email": "user@example.com",
                "isEmailVerified": true
              },
              "hashedPassword": {
                "value": "$firebasescrypt$ln=14,r=8$42xEC+ixf3L2lw==$lSrfV15cpx95/sZS2W9c9Kp6i/LVgQNDNC/qzrCnh1SAyZvqmZqAjTdn3aoItz+VHjoZilo78198JAdRuid5lQ==$Bw==$jxspr8Ki0RYycVU8zykbdLGjFQ3McFUH0uiiTvC8pVMXAn210wjLNmdZJzxUECKbm0QsEmYUSDzZvpjeJ9WmXA=="
              }
            }
          }
        ]
      }
    ]
  },
  "timeout": "5m0s"
}
```

**Key Mapping:**
- `localId` → `userId`
- `email` → `email.email` and `userName`
- `emailVerified` → `email.isEmailVerified`
- `displayName` → `profile.firstName` and `profile.lastName` (both are required; if you can't split, set `firstName` to the full display name, set a placeholder `lastName` like `"-"`, and optionally set `profile.displayName` to the full name as well)
- `passwordHash` and `salt` → `hashedPassword.value`, built as described in step 5.4
- **Omit** `passwordChangeRequired`

Users without a password, for example users who only log in with a social login, have no `passwordHash`. Import them without `hashedPassword`.

### 5.6. Import Users into ZITADEL

Use the access token from step 4.3 and call the [Admin API – Import Data](/reference/api/admin/zitadel.admin.v1.AdminService.ImportData) endpoint:

```
curl --location 'https://${CUSTOM_DOMAIN}/admin/v1/import' \
--header 'Content-Type: application/json' \
--header 'Authorization: Bearer <access-token>' \
--data @importBody.json
```

ZITADEL checks every hash at import. The import fails for a user if the verifier is not enabled or if the parameters are outside the configured limits.

### 5.7. What Happens at Login

When a user logs in for the first time, ZITADEL verifies the password with the Firebase verifier.
After a successful login, ZITADEL hashes the password again with the configured hasher and stores the new hash.
From then on the Firebase hash is no longer used for that user.

> **Note:** The signer key is part of every imported hash string. Treat the import file as a secret and delete it after the import.

## 6. Strategy 2: Bulk Import & Password Reset (Standard)

This approach imports all users at once but requires them to set a new password on their first login.
Use it if you cannot enable the `firebasescrypt` verifier.

### 6.1. Export Users from Firebase

Export your Firebase users as described in step 5.2.
This strategy does not use the Firebase password hashes.

### 6.2. Transform Firebase Data to ZITADEL Format

Map the Firebase fields to ZITADEL's schema as described in step 5.5, with these differences:

- **Omit** the `hashedPassword` object entirely
- **Include** `"passwordChangeRequired": true` to trigger password reset

**ZITADEL Import Format:**
```json
{
  "dataOrgs": {
    "orgs": [
      {
        "orgId": "<your-org-id>",
        "humanUsers": [
          {
            "userId": "firebase-user-123",
            "user": {
              "userName": "user@example.com",
              "profile": {
                "firstName": "John",
                "lastName": "Doe"
              },
              "email": {
                "email": "user@example.com",
                "isEmailVerified": true
              },
              "passwordChangeRequired": true
            }
          }
        ]
      }
    ]
  },
  "timeout": "5m0s"
}
```

### 6.3. Import Users into ZITADEL

Import the users with the same request as in step 5.6.

### 6.4. Notify Users

Send an email to your users informing them that they need to reset their password on their next login. ZITADEL will automatically prompt them to create a new password when `passwordChangeRequired` is set to `true`.

## 7. Strategy 3: Just-In-Time (JIT) Migration (Seamless)

This approach migrates users transparently during their first login after migration begins, providing a seamless experience.

### 7.1. Architecture Overview

```text
    User Login Attempt
           ↓
       Backend (Proxy)
           ↓
       Check ZITADEL
           ↓
    User exists? → Yes → Allow login
           ↓ No
    Verify with Firebase Auth REST API
           ↓
    Valid? → Yes → Create user in ZITADEL → Allow login
           ↓ No
       Reject login
```

### 7.2. Implementation Steps

#### Step 1: Set Up Login Interception

Your backend must intercept login requests and capture the plain-text password during the grace period.

**Security Requirements:**
- **HTTPS only** – Never transmit passwords over unencrypted connections
- **Do not log plain-text passwords** – Handle credentials in memory only
- **Limit grace period** – Set a reasonable migration window (e.g., 30-90 days)

#### Step 2: Verify Credentials with Firebase

When a user attempts to login, verify their credentials against Firebase using the REST API:

```
curl --location 'https://identitytoolkit.googleapis.com/v1/accounts:signInWithPassword?key=[WEB_API_KEY]' \
--header 'Content-Type: application/json' \
--data '{
  "email": "user@example.com",
  "password": "user-password",
  "returnSecureToken": true
}'
```

**Response Handling:**
- **200 OK** – Credentials are valid, proceed to Step 3
- **400 Bad Request** – Invalid credentials or user doesn't exist in Firebase

#### Step 3: Create User in ZITADEL

If Firebase validates the credentials, immediately create the user in ZITADEL using the plain-text password (ZITADEL will hash it using its native algorithm):

```
curl --location 'https://${CUSTOM_DOMAIN}/management/v1/users/human/_import' \
--header 'Content-Type: application/json' \
--header 'Authorization: Bearer <access-token>' \
--data '{
  "userName": "user@example.com",
  "profile": {
    "firstName": "John",
    "lastName": "Doe"
  },
  "email": {
    "email": "user@example.com",
    "isEmailVerified": true
  },
  "password": "user-password"
}'
```

#### Step 4: Allow Login

Once the user is created in ZITADEL, allow the login to proceed. Future logins will authenticate directly against ZITADEL.

### 7.3. Handle the Grace Period

Set a migration deadline (e.g., 90 days). After this period:

1. **Disable Firebase Authentication** for your application
2. **Migrate remaining inactive users** using Strategy 1 (Bulk Import with Password Hashes) if the `firebasescrypt` verifier is enabled, or else Strategy 2 (Bulk Import + Password Reset)
3. **Notify inactive users** that they need to reset their password, if you used Strategy 2

### 7.4. Sample Backend Implementation (Pseudocode)
```js
async function handleLogin(email, password) {
  // Check if user exists in ZITADEL
  const zitadelUser = await checkZitadelUser(email);
  
  if (zitadelUser) {
    // User already migrated, authenticate with ZITADEL
    return authenticateWithZitadel(email, password);
  }
  
  // User not in ZITADEL, verify with Firebase
  const firebaseValid = await verifyWithFirebase(email, password);
  
  if (firebaseValid) {
    // Create user in ZITADEL with plain-text password
    await createZitadelUser(email, password, firebaseValid.profile);
    
    // Authenticate with ZITADEL
    return authenticateWithZitadel(email, password);
  }
  
  // Invalid credentials
  throw new Error('Invalid email or password');
}
```

## 8. Testing the Migration

### 8.1. Test User Login

**For Strategy 1 (Bulk Import with Password Hashes):**
- Attempt to login with an imported user and their old Firebase password
- Verify that the login succeeds without a password reset
- Log in a second time to confirm that the password still works after ZITADEL stored the new hash

**For Strategy 2 (Bulk Import + Password Reset):**
- Attempt to login with an imported user
- Verify that the password reset flow is triggered
- Complete the password reset and confirm successful login

**For Strategy 3 (JIT Migration):**
- Attempt to login with a Firebase user that hasn't been migrated yet
- Verify that the login succeeds seamlessly
- Check that the user now exists in ZITADEL
- Attempt a second login to confirm authentication happens directly with ZITADEL

### 8.2. Verify User Data

Check that user data was imported correctly:

```
curl --location 'https://${CUSTOM_DOMAIN}/management/v1/users/human/_search' \
--header 'Authorization: Bearer <access-token>' \
--header 'Content-Type: application/json' \
--data '{
  "query": {
    "offset": "0",
    "limit": 100
  }
}'
```

### 8.3. Troubleshooting

**Common issues:**

- **Strategy 1:**
  - The import rejects the password hash because the `firebasescrypt` verifier is not enabled. Depending on the configured hasher, the error says the hash encoding is not supported or the password is invalid. Enable the verifier as described in step 5.3.
  - The import rejects the password hash because `mem_cost` or `rounds` are outside the configured limits. Adjust `SystemDefaults.PasswordHasher.Limits.FirebaseScrypt`.
  - Every login fails with a wrong password error. Check that the signer key and the salt separator are the ones of your Firebase project, and that `mem_cost` and `rounds` are correct.
  - Login fails with an internal error for users who have not logged in since the import. The `firebasescrypt` verifier was disabled. Enable it again as described in step 5.3.
  - Import API timeout (reduce batch size)
  - Malformed JSON (validate against ZITADEL schema)

- **Strategy 2:**
  - Users not receiving password reset emails (check email configuration)
  - Import API timeout (reduce batch size)
  - Malformed JSON (validate against ZITADEL schema)

- **Strategy 3:**
  - Firebase API authentication errors (verify Web API Key)
  - HTTPS certificate issues (ensure valid SSL/TLS)
  - User creation failures (check ZITADEL service account permissions)

#### Where to check logs and get help

You can verify that users were imported by calling the **events endpoint** and checking for the following event type:

"user.human.added"

Example request:

```
curl --location 'https://${CUSTOM_DOMAIN}/admin/v1/events/_search' \
--header 'Authorization: Bearer <token>' \
--header 'Content-Type: application/json' \
--data '{
  "asc": true,
  "limit": 1000,
  "event_types": [
    "user.human.added"
  ]
}'
```
